## Ejercicio 09: experimentar con `GOGC` y `gctrace`

Usá el programa del ejercicio anterior o adaptalo para realizar muchas
asignaciones controladas. Ejecutalo varias veces con configuraciones distintas:

```bash
GODEBUG=gctrace=1 GOGC=25 go run .
GODEBUG=gctrace=1 GOGC=200 go run .
```

Compará la frecuencia de los ciclos, la memoria utilizada y el tiempo total.
Relacioná el resultado con el intercambio entre trabajo del GC y memoria: un
`GOGC` menor suele provocar ciclos más frecuentes y uno mayor permite más
memoria antes de iniciar otro ciclo.

Probá `GOGC=off` sólo con una carga pequeña y acotada. Documentá por qué no es
una configuración segura para ejecutar un programa que asigna memoria sin
límite.

### Cómo leer la salida

Una línea como esta:

```text
gc 8 @0.007s 7%: 0.008+0.24+0.002 ms clock, ... 10->10->10 MB, 10 MB goal, 0 MB stacks, 0 MB globals, 16 P
```

describe un ciclo del garbage collector:

- `gc 8` es el número de ciclo dentro de ese proceso.
- `@0.007s` es el tiempo transcurrido desde que comenzó el proceso.
- `7%` es el porcentaje aproximado de tiempo de CPU dedicado al GC hasta ese
  momento.
- Los tres tiempos después de `ms clock` corresponden, de forma resumida, a
  las fases de preparación, marcado y finalización del ciclo. Los valores
  posteriores a `ms cpu` muestran el trabajo de CPU de esas fases y de tareas
  relacionadas, por lo que no tienen por qué coincidir con el tiempo de reloj.
- `10->10->10 MB` significa memoria del heap antes del ciclo, después de la
  asignación y después de liberar lo que ya no era alcanzable.
- `10 MB goal` es el objetivo aproximado de heap que dispara el siguiente ciclo.
  No es un límite máximo.
- `0 MB stacks`, `0 MB globals` y `16 P` informan, respectivamente, memoria de
  stacks, memoria global considerada y la cantidad de procesadores lógicos que
  usa el runtime.

### Diferencias entre las ejecuciones

Con `GOGC=25`, el objetivo del heap crece poco después de cada ciclo. Por eso el
GC se ejecuta muchas veces (en la salida aparecen decenas de líneas), mantiene
el heap relativamente pequeño y dedica una proporción mayor del tiempo al
recolector. Se observa, por ejemplo, que el objetivo suele estar entre `1 MB`
y `13 MB`.

Con `GOGC=200`, el runtime permite que el heap crezca aproximadamente dos veces
su tamaño vivo antes de iniciar otro ciclo. En consecuencia hay muchos menos
ciclos, pero la memoria llega a valores mayores (`24 MB`, `26 MB`, etc.). El
programa hace menos trabajo de GC, aunque eso no significa que siempre termine
más rápido: usa más memoria y el resultado depende de la carga y del entorno.

Con `GOGC=off`, el GC automático queda desactivado. Por eso no aparecen líneas
`gc` en la última ejecución. Las asignaciones siguen ocurriendo y la memoria no
se recupera automáticamente mientras el proceso continúa; con una carga sin
límite esto puede terminar en agotamiento de memoria. Que este ejemplo termine
bien sólo significa que su carga es pequeña y acotada.

### Por qué hay grupos repetidos de líneas

`go run .` primero compila el programa y luego lo ejecuta. Como `GODEBUG` se
hereda, también puede mostrar líneas `gc` del proceso del compilador. Las líneas
que aparecen junto a `# learning-go/chapters/06-pointers/ex09` pertenecen a esa
compilación; las que aparecen después corresponden al programa del ejercicio.
Además, cada proceso empieza nuevamente en `gc 1`, y los tiempos y decisiones
exactas pueden cambiar entre ejecuciones, versiones de Go y máquinas.

La diferencia fundamental es el intercambio entre memoria y trabajo: un
`GOGC` bajo recupera memoria con mayor frecuencia, mientras que uno alto deja
crecer más el heap para reducir la frecuencia del GC.
